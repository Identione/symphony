## 1. HIGH — Sidecar crashes on any stdin line over 64 KiB

**Where:** `elixir/priv/claude_agent/symphony_claude_agent/sidecar.py:813,818` (`_stdin_lines`)

`asyncio.StreamReader(loop=loop)` is constructed without a `limit=` argument, so it uses
CPython's default 64 KiB line limit. `reader.readline()` raises `ValueError` ("Separator is
found, but chunk is longer than limit") when a single line exceeds the limit. Nothing
catches it: it propagates out of the `async for line in _stdin_lines()` loop in `_serve()`
and out of `asyncio.run()` in `main()` (which only catches `KeyboardInterrupt`), killing the
whole sidecar process.

**Failure scenario:** any Symphony→sidecar envelope over ~65,536 bytes on one line — most
plausibly a `tool_result` for `linear_graphql` (the Elixir side puts no size cap on the
GraphQL response before writing it to the port; the sidecar's own `cap_tool_result_text`
truncation runs only *after* the line has been parsed) or a large rendered turn prompt.
The Elixir side does see the port `:exit_status` (no permanent hang), but the in-flight
Claude session is destroyed and restarted from scratch, discarding conversation state.

**Fix direction:** pass an explicit large `limit=` to `StreamReader` (e.g. 16 MiB), and/or
cap `tool_result` payloads on the Elixir side before writing to the port.

**Fixed (2026-07-05):** `_STDIN_LINE_LIMIT = 16 MiB` passed to the StreamReader. Regression
test: `tests/test_stdin_lines_line_limit.py::test_stdin_lines_yields_line_larger_than_64kib`
(reproduced the `ValueError` before the fix).

## 2. HIGH — Codex adapter ignores `:turn_timeout_ms`, and its timeout is inactivity-based, not wall-clock

**Where:** `elixir/lib/symphony_elixir/codex/app_server.ex:89-94` (opts read), `:360`
(`await_turn_completion`), `:366-380` (`receive_loop`); callers at
`elixir/lib/symphony_elixir/agent_runner.ex:381` and `:973-975`.

Two related defects:

1. `Codex.AppServer.run_turn/4` reads only `:on_message` and `:tool_executor` from `opts`.
   The `:turn_timeout_ms` option — passed by both the normal turn path
   (`agent_runner.ex:381`, `Config.active_turn_timeout_ms/1`) and the overseer wind-down
   turn (`agent_runner.ex:973-975`, default 120,000 ms) — is silently ignored;
   `await_turn_completion/2` always uses the global `Config.settings!().codex.turn_timeout_ms`
   (default 3,600,000 ms). The wind-down turn, designed as a bounded one-shot "cannot
   re-enter the loop" safety mechanism, can therefore run 30× longer than intended under
   the Codex adapter. The Claude adapter honors the option correctly
   (`claude/app_server.ex:80`).
2. `receive_loop/4` uses `after timeout_ms` on each `receive`, resetting the clock on every
   incoming message. Since an active Codex turn emits events continuously, the configured
   `turn_timeout_ms` acts as an **inactivity** timeout, not a wall-clock cap — a turn that
   keeps producing output is effectively unbounded. The Claude adapter's `do_collect/3`
   implements a proper absolute deadline (`claude/app_server.ex:431-432`); Codex should too.

**Fix direction:** thread `opts[:turn_timeout_ms]` into `await_turn_completion`, and track
an absolute monotonic deadline in `receive_loop` (recomputing the remaining `after` value
per message) as the Claude adapter does.

**Fixed (2026-07-05):** both defects — `run_turn/4` now honors `opts[:turn_timeout_ms]`
(falling back to `codex.turn_timeout_ms`), and the receive loop enforces an absolute
monotonic deadline threaded through all recursion paths. Tests:
`test/symphony_elixir/codex_app_server_timeout_test.exs` (2 tests, both red pre-fix).

## 3. HIGH severity / low likelihood — Worker-host workspaces skip the containment check; remote `rm -rf` can escape `workspace.root`

**Where:** `elixir/lib/symphony_elixir/workspace.ex:215-217` (`workspace_path_for_issue`
worker-host branch), `:219-221` (`safe_identifier`), `:446-458` (`validate_workspace_path`
worker-host branch), `:251-260` (remote `rm -rf`).

`safe_identifier/1` keeps `[a-zA-Z0-9._-]`, so an identifier consisting only of dots
(`"."`, `".."`) passes through unchanged. For **local** runs the path is canonicalized and
strictly containment-checked under `workspace.root` (`workspace.ex:209-213`, `:418-444` —
covered by the symlink-escape tests). For **SSH worker-host** runs the path is a plain
`Path.join(root, safe_id)` and validation only rejects empty strings and control
characters — no containment check. With identifier `".."` the remote workspace resolves to
the parent of `workspace.root`; cleanup paths (`remove/2`, and
`remove_created_workspace_after_hook_failure/4`) then run `rm -rf "$workspace"` there —
i.e. recursively delete the parent of the workspace root (or, with `"."`, the entire root
and every concurrent issue workspace on that host).

**Likelihood note:** real Linear identifiers (`TEAM-123`) cannot produce this; it requires
an unusual identifier from a custom/in-memory tracker. But the local branch defends against
exactly this class of untrusted input, and the remote branch — where the blast radius is a
remote `rm -rf` — does not. Defense-in-depth gap.

**Fix direction:** apply the same reject-list to the worker-host branch: refuse
identifiers that normalize to `"."`/`".."`/empty, and verify `Path.join(root, safe_id)`
stays under `root` (lexically, since the remote FS can't be canonicalized locally).

**Fixed (2026-07-05):** the worker-host branch of `workspace_path_for_issue/2` now rejects
dot-only/empty identifiers with `{:error, {:unsafe_workspace_identifier, _}}` plus a
lexical containment backstop. Test: `"workspace rejects dot-only issue identifiers on
worker hosts without invoking ssh"` in `workspace_and_config_test.exs` (red pre-fix: `".."`
sailed through to the remote path). Local branch untouched (already guarded).

## 4. MEDIUM — Legacy `codex:` block is wholesale-replaced (not merged) when `agent.codex:` also exists, silently dropping operator settings

**Where:** `elixir/lib/symphony_elixir/config/schema.ex:872-894` (`apply_legacy_codex_alias/1`)

When WORKFLOW.md contains both a legacy top-level `codex:` block and a nested
`agent.codex:` block, the `{_, nested} when is_map(nested)` branch does
`Map.put(config, "codex", nested)` — replacing the entire top-level block with the nested
map rather than merging per-field. Any field set only at the top level silently reverts to
its compiled default, with no warning. Empirically verified: with `codex: {turn_timeout_ms:
9999}` plus `agent: {codex: {read_timeout_ms: 111}}`, both `settings.codex.turn_timeout_ms`
and `settings.agent.codex.turn_timeout_ms` come back `3_600_000`. Affects every `Codex`
field, including `approval_policy` and `thread_sandbox` — meaning a mid-migration operator
can silently *lose a security-relevant setting* back to its default. The comment ("when
both are present, nested wins") reads as per-field precedence; the implementation is block
replacement. Existing regression tests only cover same-field-in-both or one-block-only
cases.

**Fix direction:** deep-merge with nested taking per-field precedence
(`Map.merge(top, nested)`), or log a loud warning when both blocks are present.

**Fixed (2026-07-05):** recursive `deep_merge/2` (nested wins per-field, recursing into
sub-blocks like `quota`); the merged map lands in both `codex` and `agent.codex`. Test:
`"legacy top-level codex and nested agent.codex deep-merge per field, nested winning
conflicts"` in `claude_adapter_config_test.exs` (red pre-fix: top-only field reverted to
compiled default).

## 5. MEDIUM — `agent.max_sessions_per_issue` cap is not enforced when the escalation side-effect fails

**Where:** `elixir/lib/symphony_elixir/orchestrator.ex:678-722` (`escalate_session_budget`),
`:578-586` (`apply_deterministic_failure_result` catch-all), `:396-421` (`retry_agent_down`);
`elixir/lib/symphony_elixir/orchestrator/retry_policy.ex:27-37,127-128`.

When an issue hits the cumulative session cap, escalation runs as a supervised async task
(Linear comment + state move). Two failure paths relaunch the over-cap session instead:

1. **Spawn failure** (`orchestrator.ex:707-722`): explicitly falls back to a 1 s
   continuation retry — one extra full session per failure, unbounded while the task
   supervisor is saturated. (The comment marks this as an intentional "don't strand the
   issue" trade-off, but the cap is a cost/runaway control and this loop is unbounded.)
2. **Side-effect failure** (e.g. transient Linear API error): the catch-all at `:578-586`
   routes to `retry_agent_down` with the synthetic reason
   `{:agent_run_failed, :max_sessions_per_issue, :session_cap}`. Because
   `:max_sessions_per_issue` is **not** in `RetryPolicy.@recognized_codes`, it normalizes
   to `:unknown` → generic backoff → a brand-new agent session is dispatched despite the
   exhausted budget. Each cycle of "run full session → clean exit → cap check → escalation
   fails" burns an entire over-cap agent session for as long as the tracker error persists.

`orchestrator_session_budget_test.exs` covers only the successful-escalation path.

**Fix direction:** add `:max_sessions_per_issue` to the recognized codes with a `:no_retry`
(or escalation-retry-only) policy, and make the failure paths retry *the escalation
side-effect* rather than the agent session.

**Fixed (2026-07-05):** `:max_sessions_per_issue` added to `@recognized_codes` with a
`:no_retry` policy — a failed escalation side-effect now blocks the issue instead of
relaunching an over-cap session. Tests: `orchestrator_retry_policy_test.exs` (policy unit)
and `"a failed escalation side effect blocks the issue instead of dispatching another
over-cap session"` in `orchestrator_session_budget_test.exs` (red pre-fix: issue landed in
`retry_attempts` with generic backoff). The spawn-failure fallback branch
(`orchestrator.ex:707-722`) is left as-is — its continuation-retry is explicitly documented
as an intentional "don't strand the issue" trade-off.

## 6. MEDIUM — `tracker.assignee` "me" sentinel is case-sensitive; wrong casing silently stops all work pickup

**Where:** `elixir/lib/symphony_elixir/linear/client.ex:598-609` (`build_assignee_filter`),
`:630-635` (`normalize_assignee_match_value` — trims only, no downcase).

`assignee: "Me"` in WORKFLOW.md (or `LINEAR_ASSIGNEE=ME` in the environment — the env value
passes through `resolve_secret_setting` untouched) misses the `"me"` clause and falls into
the literal-ID branch, building a filter whose only match value is the string `"Me"`. Since
real assignee IDs are Linear UUIDs, `assigned_to_worker?/2` returns `false` for every
issue and the instance silently dispatches nothing. No error or warning is logged anywhere
on this path, making the misconfiguration very hard to diagnose. No test pins the
case-sensitive behavior as intentional; the sentinel is documented only as lowercase `"me"`.

**Fix direction:** compare case-insensitively for the sentinel (`String.downcase(normalized)
== "me"`), or at minimum log a warning when a configured assignee matches zero issues over
several consecutive polls.

**Fixed (2026-07-05):** the sentinel is now matched case-insensitively after trimming
(`"Me"`, `"ME"`, `" me "` all resolve the viewer); non-sentinel values (including prefix
values like `"meeting"`) stay byte-exact literals. Tests in
`workspace_and_config_test.exs` via the new `resolve_assignee_filter_for_test/2` seam.

## 7. MEDIUM — Sidecar docstring claims a "workspace-boundary `PreToolUse` hook" that does not exist

**Where:** `elixir/priv/claude_agent/symphony_claude_agent/sidecar.py:8` (docstring) vs
`:577-617` (the only PreToolUse/PostToolUse hooks).

The module docstring states: "Anything Symphony does not pre-approve via `dontAsk` +
`allowed_tools` + the workspace-boundary `PreToolUse` hook is denied." No such hook exists:
the registered `PreToolUse`/`PostToolUse` hooks are pure lifecycle notifications
(`tool_started`/`tool_finished`, unconditionally `return {}`), and the PostToolUse output
hook only truncates oversized output. There is no path/workspace containment check anywhere
in the sidecar — the actual containment posture rests entirely on `permission_mode: dontAsk`
+ the Elixir-supplied `allowed_tools` list + whatever cwd-scoping the Claude CLI itself
applies. The claim has been in the docstring since the file's first commit (`05e80ec`);
CLAUDE.md's "workspace-cwd boundary" description inherits the same overstatement. If a
workflow ever whitelists `Bash`, nothing in the sidecar prevents absolute-path access
outside the workspace.

**Fix direction:** either implement the described deny hook (reject file-tool paths and
Bash cwd escapes outside the workspace root) or correct the docstring/CLAUDE.md so
operators don't rely on a nonexistent layer.

**Fixed (2026-07-05):** docstring corrected — it now states that denial rests on
`permission_mode=dontAsk` + the `allowed_tools`/`disallowed_tools` whitelist, and that the
hooks here are notification/truncation-only. (Implementing an actual workspace-boundary
deny hook remains available as a hardening feature if wanted — tracked nowhere yet.)
README.md did not contain the false claim.

## 8. LOW — With `assignee: "me"`, the viewer identity is re-resolved via GraphQL on every fetch

**Where:** `elixir/lib/symphony_elixir/linear/client.ex:588-596` (`routing_assignee_filter`),
`:611-628` (`resolve_viewer_assignee_filter`); call sites `:197` (`fetch_candidate_issues`)
and `:235` (`fetch_issue_states_by_ids`).

Every candidate fetch and every issue-state fetch issues a fresh `viewer` GraphQL query to
re-derive the same viewer ID — `fetch_issue_states_by_ids/1` alone is called from several
orchestrator sites per tick (reconciliation, graph expansion, dispatch). This multiplies
Linear API traffic against the documented 2,500 req/hr budget, and because the fetch is
gated on `with {:ok, assignee_filter} <- routing_assignee_filter()`, a transient failure or
rate-limit on this *ancillary* query aborts the whole data fetch that was never attempted.

**Fix direction:** cache the resolved viewer ID (process state or `:persistent_term`) with
periodic/on-error refresh.

**Fixed (2026-07-05):** viewer ID cached in `:persistent_term`, keyed on a hash of the
active API token (never the raw secret); only successful resolutions are cached, errors
retry next call. `reset_viewer_cache/0` added for test isolation. Tests assert exactly one
viewer query across consecutive resolutions.
